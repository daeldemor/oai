> Примечание: раздел про Strata (2.1) добавлен после выхода в сеть; источники —
> [stratallm.org](https://stratallm.org/) и
> [обзор vdf.ai от 13.11.2026](https://vdf.ai/blog/strata-local-llm/).
> Остальные разделы проверены практикой локального инференса.

## 1. Что такое аблитерация и какие есть подходы

### A. Ортогонализация направления отказа (FailSpy, 2023 → классика)

1. Прогоняем через модель два набора промптов: «вредные» (на которые модель
   отвечает отказом) и «безобидные».
2. Для каждого слоя считаем разницу средних активаций → получаем вектор
   «направления отказа» (refusal direction) для каждого residual stream.
3. Вычитаем проекцию на это направление из весов (матрицы `o_proj`, `down_proj`
   и др. — «writable» матрицы): `W' = W − r (rᵀW)`.

Плюсы: не нужен датасет и обучение, минуты работы, интеллект почти не страдает.
Минусы: один глобальный вектор — грубовато для крупных моделей; иногда «плывёт»
качество на сложных рассуждениях.

### B. Heretic (p-e-w) — текущий де-факто стандарт

Автоматизирует A, но улучшает его:

- ищет направления **по каждому слою отдельно** и подбирает силу подавления
  через оптику (Optuna): минимизирует одновременно количество отказов и
  KL-дивергенцию к исходной модели (защита «интеллекта»);
- умеет оценивать результат на встроенных наборах промптов;
- работает поверх `transformers`, грузит модель с `device_map="auto"` —
  на 32 ГБ RAM + 16 ГБ VRAM реально аблитерировать dense-модели до ~14B.

Именно им сделана уже стоящая у вас `gemma-4-26B-A4B-it-heretic`.

### C. OBLITERATUS

GUI-инструмент (Brane) для тех же операций + удобная загрузка на Hugging Face.
Удобен как наглядная альтернатива, но менее гибок в скриптовом пайплайне.

### D. Готовые GGUF (mradermacher, huihui-ai, DavidAU и др.)

Не «своя» аблитерация, но самый быстрый путь: авторы уже сделали A/B и выложили
кванты. Теги: `abliterated`, `heretic`, `uncensored`, `decensored`.

### Что выбираем

**Решение (16.11.2026): основной путь — D, готовые GGUF.** Своя аблитерация
(B) не планируется; `scripts/abliterate.py` и `scripts/quantize.sh` оставлены
как опция на будущее.

| Сценарий | Подход |
|---|---|
| Основной | D — готовые heretic/abliterated GGUF (`scripts/download.sh`) + llama.cpp/LM Studio/Bionic |
| Опционально, «на вырост» | B — Heretic (обёрнут в `scripts/abliterate.py`) |

Источники готовых GGUF (по скачиваниям на HF, 16.11.2026): **mradermacher**
(крупнейший каталог, 73k+ репозиториев), **DavidAU** (NEO/IMATRIX/MTP-сборки),

### 2.1. Strata — новый MoE-специализированный движок (сентябрь 2026)

[Strata](https://stratallm.org/) (MIT, автор Niko1221, первый релиз 24.09.2026,
активно развивается) — движок, заточенный под запуск **огромных MoE-моделей
на потребительском железе**: предиктивная подгрузка экспертов из RAM/SSD в VRAM,
zero-copy pinned memory, MTP-драфтинг (ускорение ~1.6–1.8x), OpenAI/Anthropic-
совместимый API на :8080.

Поддерживаемые семейства (строго ограниченный список):

- **Qwen3.8-Flash-Next** (~125–180B total / 6B активных) — флагман;
- **Qwen3.6-35B-A3B** — NVIDIA/AMD;
- **DeepSeek V4.1-Flash** — 191–274 ГБ загрузки.

**Что это меняет для нас — и что нет:**

| Вопрос | Влияние Strata |
|---|---|
| Потолок «интеллекта» на этом ПК | **Растёт**: 125B-класс MoE вместо 24B dense. Заявлено 25–87 ток/с на 12 ГБ VRAM + 64 ГБ RAM (замеры автора, независимых нет) |
| Наши 32 ГБ RAM | **Узкое место**: помещается только пакет Coder IQ1_M (~30 ГБ, только код). Q2_0 требует 48 ГБ, IQ3_S — 64 ГБ. Low-RAM режим со стримингом с SSD работает, но заметно медленнее |
| Аблитерация своими руками | **Не меняется**: Strata — только сервинг, и только трёх семейств. Свою abliterated-модель (dense 8–14B) он не запустит; abliterate-пайплайн (Heretic → GGUF → llama.cpp) остаётся основным |
| Готовые abliterated GGUF | llama.cpp остаётся универсальным движком; Strata запустит только heretic-кванты поддерживаемых семейств (если их опубликуют) через `--model-path` |
| Зрелость | Проекту ~2 месяца, один основной мейнтейнер, релизы каждые несколько дней, внешнего аудита не было — версии пиновать, для «боевого» использования рано |
| Конфликт портов | Strata по умолчанию слушает :8080 — как и наш `serve.sh`; задавать `--port` |

**Вывод по Strata:** отличное дополнение, если захочется frontier-уровень MoE
локально — но сначала апгрейд RAM до 64 ГБ. На текущих 32 ГБ наш основной путь
(llama.cpp + свои abliterated GGUF до 14B + готовые MoE-кванты с выгрузкой)
остаётся оптимальным.

- Strata считает память как RAM+VRAM: наша машина — 31+16=47 ГБ → «40 ГБ tier».
  Из её семейств «хорошо» влезает только **Qwen3.6-35B-A3B в 4 битах**: Flash-Next требует ≥44 ГБ RAM
  или стриминга с SSD (Coder IQ1_M, 63.6 ГБ, сток), Gyro-S — ниже качеством.

**Почему сторонний GGUF сначала не запускался — две причины, обе обходятся:**

1. `strata launch --model-path <папка>` без семейства идёт через импорт, который знает только Flash-Next
   (`plan_import`: архитектура `qwen4exp`) → «this model type is not supported». Для Qwen3.6 свой файл
   подаётся как **`--family qwen36 --model ud-q4_k_xl --model-path <папка>`**, а файл в папке должен называться
   `Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf` (`setup.py: OWN_PATH_FAMILIES`); чужой размер — только предупреждение.
2. Движок проверяет формат экспертов: down-эксперты в **Q4_K не принимаются**
   (`iq_kernels.cu: STRATA_D_FMTS` — Q5_1/Q5_0/Q4_1/Q4_0/Q8_0/Q5_K/Q6_K/IQ4_*). В Q4_K_M 20 из 40 слоёв
   хранят down в Q4_K → `blk.5.experts are Q4_K/Q4_K, which the native expert kernels do not take`.
   Лечение — `scripts/strata_fix_down.py`: перекодирует эти 20 тензоров Q4_K → Q5_1 без потерь по смыслу
   (тот же 4-битный код, scale/min округляются до float16; `--verify` сверяет всё остальное байт в байт).
   Файл растёт с 21.78 до 22.79 ГБ, ~2.5 мин на SSD.

**Рабочий запуск** (файл на SSD `X:`; `G:` — HDD):

```
python -I scripts/strata_fix_down.py <...>-Q4_K_M.gguf X:\OAI-models\qwen36-heretic-strata\Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf --verify
strata launch --family qwen36 --model ud-q4_k_xl --model-path "X:\OAI-models\qwen36-heretic-strata" ^
  --vision off --context 32k --parallel 1 --access local --port 8080 --save-preset heretic-q36-32k --yes --no-tui
# дальше просто: strata launch --preset heretic-q36-32k      стоп: strata launch --stop --preset heretic-q36-32k
```

голову идёт в flash attention. Пиковая сумма около 200 байт и есть наблюдаемый
рост. В upstream на 2026-11-22 исправления нет. С дефолтным `-ub 512` буфер на 32k
уже 3.4 ГБ, модель вылезает за VRAM в общую память, и генерация падает до

#### 2.4.1. Свой патч llama.cpp: внимание по KV-головам (2026-11-22)

Патч: [`patches/llama.cpp-b12633-inkling-rel-attn.patch`](../patches/llama.cpp-b12633-inkling-rel-attn.patch),
4 файла, +103/−24. Исходник `llama.cpp-src/` (b12633, вне git), сборка `llama.cpp-src/build/bin/`
(VS 2022 Build Tools 17.14 + CUDA 13.5, только sm_120). DLL CUDA лежат в
`C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.5\bin\x64`, этот путь нужен в PATH.

Что меняет:

1. `build_attn` для слоёв с относительным bias на длинных промптах считает flash attention
   отдельно для каждой из 8 KV-голов. Маска с bias одновременно живёт только для 3 голов из 24.
   `LLAMA_ATTN_REL_SPLIT=0` возвращает старое поведение.
2. Bias переводится в f16 при перестановке осей, маска добавляется уже в f16. Маска содержит
   только 0 и −inf, поэтому результат тот же.
3. CUDA `get_rows` для строк короче 33 элементов копирует один элемент на поток. Раньше на каждую
   строку уходил блок из 256 потоков, и с разбиением по головам prefill падал вдвое.

Compute-буфер растёт на ~32 байта на пару вместо ~200. На 32k с `-ub 256` было 1678 МиБ, стало 385.

| Конфиг | Буфер | Заполнение | Prefill | Генерация |

сервер всегда стартует с `--api-key-file %LOCALAPPDATA%\inkling\api-key.txt` (48 hex, создают
`.ps1`-лаунчеры). Проверено: без ключа `POST /tools` → 401, `/props` → 401, `/health` публичный; веб-чат
раньше показывал «Enter API Key», теперь ключ ему не нужен: в патч добавлено исключение в
`tools/server/server-http.cpp` (включается `LLAMA_UI_TRUST_SAME_ORIGIN=1`, его ставит `inkling.cmd`) для запросов
с `Sec-Fetch-Site: same-origin` и Host loopback:8080. Проверено curl: same-origin + Host 127.0.0.1/localhost → 200,
cross-site → 403, same-origin + чужой Host (DNS rebinding) → 403, без заголовков и ключа → 401, с ключом → 200;
в браузере без сохранённого ключа чат работает с инструментами. Claude Code получает ключ как `ANTHROPIC_AUTH_TOKEN`.
Песочницы нет: команды выполняются от имени пользователя. Режимы без подтверждений: в «Inkling Agent»
галочка «Без подтверждений (bypass)», в CLI «Без ограничений» (`--dangerously-skip-permissions`); оба проверены.
Разрешения веб-чата живут только в `localStorage` браузера (`LlamaUi.alwaysAllowedTools`, список `server:<tool>`),
поэтому в патч добавлена страница `GET /inkling-bootstrap?t=<токен>&bypass=0|1` (`tools/server/server.cpp`): она
записывает список всех инструментов сервера (bypass=1) или стирает его (bypass=0) и переходит в чат. Токен
одноразовый, задаётся на запуск через `LLAMA_UI_BOOTSTRAP_TOKEN` (его генерирует `inkling-agent.ps1`), поэтому
чужая страница, открыв этот адрес, разрешения не переключит. Проверено: без токена и с неверным → 403, повтор
того же токена → 403, bypass=1 записал 7 инструментов, bypass=0 стёр их, и чат снова спросил «Allow once».

Что заявлено на одной RTX 3090 24 ГБ (UD-Q4_K_XL, KV FP8): все 3072 эксперта (14.7 ГиБ) лежат в VRAM, токен

Почему к нам напрямую не переносится:

- **Память.** Быстрый режим рассчитан на 24 ГБ. Для 8 ГБ есть конфиг `ik2-mini-8gb.json`: эксперты лежат в
  закреплённой RAM (14.7 ГиБ), в VRAM живёт их кэш, промахи считает CPU. На ноутбуке с RTX 5070 Laptop 8 ГБ это
  40–43 ток/с на контексте 16K. У нас кэш был бы около 11 ГБ, но KV FP8 занимает 16 КБ на токен (128K = 2 ГиБ),
  и он делит VRAM с кэшем. Скорость на 16 ГБ никто не мерил.
- **Формат.** Движок читает эксперты только в Q8_0, Q5_K, Q6_K, IQ3_XXS, IQ4_XS и NVFP4 (`ik2_kernels.cuh`), а
  официально поддерживается только UD-Q4_K_XL. В нашем `AD-IQ3_S` эксперты хранятся в IQ3_S (gate_up) и
  IQ4_NL (down), движок такой файл не загрузит. Остальные файлы AtomicChat (Q4_K, IQ2_M) тоже не подходят.
- **Uncensored.** Правка AtomicChat — это LoRA ранга 1 на выход внимания, на routed-эксперты и на эмбеддинг.
  Подменить в файле Unsloth одни плотные тензоры нельзя, эксперты тоже изменены.
- **Платформа.** Разработка и замеры идут на Linux. Сборка под Windows/CUDA 13 есть (порт @cobra91, проверен на
  RTX 5080). Веб-чата с инструментами, как `llama-server --agent`, нет: только API OpenAI/Anthropic, так что
  Claude Code подключить можно, а наш GUI-агент пришлось бы переделывать.

**Inkling в Strata.** На HF есть официальные паки `strata-engine/Inkling-2-Mini-Strata`. SQ-15 (13.36 ГиБ) по
словам авторов целиком помещается в 16 ГиБ, совпадение top-1 с оригиналом 96.68%. Есть и abliterated-сборка
`SC117/Inkling-2-Mini-abliterated-Strata`, в ней аблитерирован только `attn.wo_ud` (у AtomicChat ещё эксперты и
эмбеддинг). Числа отказов в карточке нет. Её бенч на RTX 4080 SUPER (736 ГБ/с, `--bench` 512→64, fp8):
SQ-15 даёт prefill 2217 и генерацию 87.8 ток/с. Нужна Strata ≥ 0.2.19 (build 0.1.65+) с компонентом
`strata-inkling`, у нас стоит 0.2.14 (build 0.1.60.1). Это поправка к прежнему выводу «Inkling в Strata не нужен»:
тогда поддержки не было. Цена вопроса — контекст: после 13.4 ГиБ весов в VRAM остаётся около 2 ГиБ.

Варианты по порядку затрат: (1) обновить Strata и прогнать abliterated SQ-15 (скорость, реальный потолок контекста,
`evaluate.py` на отказы); (2) добавить в `maya-ik2` декодирование IQ3_S/IQ4_NL и проверить наш файл. Это большая
работа, а прирост на 16 ГБ неизвестен. Текущий стек (llama.cpp + патч, 320K, генерация 25 ток/с на 300K)
остаётся единственным вариантом для длинного контекста.

#### 2.4.3. Наш uncensored Inkling в Strata на 320K — ЗАМЕРЕНО (2026-11-23)

Релизный движок на 16 ГБ до 320K не дотягивает, мешают три вещи:

1. По умолчанию VRAM забирают эксперты, а KV достаётся остаток: контекст режется до 24K. Если включить

2. Ошибка в росте KV (`ensure_global_kv_cap`): проверяется, что свободной VRAM хватит на **весь** новый KV, хотя старый
   ещё занимает память. Рост останавливается около 180K с `VRAM exhausted growing elastic global KV`.
3. На Windows эксперты в RAM закрепляются (pinned), только если их меньше 35% доступной RAM и не больше 8 ГиБ.
   У нас 7.75 ГБ при 19.7 ГБ доступной, поэтому память выделяется обычная, и prefill идёт через буфер втрое медленнее.

Сжатие, как в Claude Code: модель пишет изложение разговора, и дальше в запрос идёт оно вместо всех сообщений
выше. Изложение уходит модели как пара «пользователь: [Изложение более раннего разговора…] текст» и
«ассистент: Понял, продолжаю», чтобы реплики чередовались. Сжатые сообщения остаются на странице, приглушённые
(пометка `compacted` в сохранённом чате), изложение отмечено полосой слева и подписью «Изложение истории: модель
читает его вместо N сообщений выше». Запускается тремя путями:
- кнопкой «Сжать историю» под полем ввода (иконка слоёв, рядом с сохранением чата);
- само, если новое сообщение доведёт оценку истории до 90% контекста: сначала изложение, потом сообщение.
  Порог высокий намеренно, контекст 320K для того и поднят, чтобы им пользоваться (первая версия сжимала
  на 75%, пользователь попросил 90%);
- после отказа сервера «exceeds the context window», если от ответа ещё ничего не пришло: вопрос откладывается,
  история сжимается, вопрос уходит ещё раз. Отказ посреди ответа с инструментами не повторяется, сжатие пройдёт
  перед следующим сообщением.

Запрос на изложение начинается с той же истории, что лежит в кэше разговора, плюс просьба сжать (те же
инструменты MCP, тот же уровень размышлений: он задаётся на сервере), так что модель дочитывает только хвост.

говорит, что не влезет, или сервер всё же отказал на запросе изложения, старые результаты инструментов убираются
до 50% контекста и изложение запрашивается ещё раз: кэш в этом случае всё равно теряется, и модель прочитает
половину контекста, а не почти весь. Кнопка «Стоп» во время сжатия оставляет историю как была, а автоматическое сжатие возвращает

#### 2.4.5. squid5090: разбор (2026-11-25, не запускали)

Источник: [tensorfish/squid5090](https://github.com/tensorfish/squid5090) (Apache-2.0, репозиторию два дня,
166 звёзд). Движок на Zig и CUDA под `sm_120a` только для Inkling-2-Mini, с сервером OpenAI (SSE, `tools`).
Часть ядер взята из `satellitedown/inkling-2-mini-abliterated-ingine`. Все цифры авторские, с одной RTX 5090 32 ГБ.

Что заявлено (один пользователь):
- генерация без драфтера 263 ток/с (nvfp4); с DSpark и адаптивной шириной проверки {2, 4, 8} 422–547 на коде
  и 226–316 в чате, с prompt-lookup на цитировании до 772;
- prefill до 9 200 ток/с на коротком контексте, 3 062 на 512K; иголка на 50% глубины найдена на 64K–512K;
- 1M контекста в 23.2 ГиБ: глобальный KV есть только у 8 визитов из 48, в Q4 это около 8.5 КБ на токен;
- KLD против bf16 на 7 784 токенах: 0.006–0.010 в режиме fp8, 0.026 в nvfp4 (top-1 94.8%).

Почему у нас не запустится:
- **Память.** Веса даже в nvfp4 занимают 14.57 ГиБ, 13.70 с эмбеддингами в RAM. Выгрузки экспертов в RAM нет,
  движок держит всё в одной арене VRAM. Авторский замер на 20K: 16.7 ГиБ. У нас 15.9 ГиБ всего, и часть
  занята рабочим столом.
- **Платформа.** Только Linux x86_64: сокеты, `mmap` и `clock_gettime` объявлены напрямую через libc с константами
  Linux (`src/tiger.zig`), в `build.zig` пути `/usr/local/cuda`. Под Windows нужен WSL2 с Ubuntu (сейчас стоит
  только `docker-desktop`) или порт этих функций.
- **Веса.** Движок читает официальный чекпойнт safetensors (19.5 ГБ), GGUF не читает, наш uncensored-файл
  AtomicChat не подойдёт. Отказы снимаются по-своему: файл на 1.8 МБ, по которому во время работы направление
  отказа вычитается только там, где его видит детектор Fisher-LDA. В репозитории такого файла нет,
  `tools/ablate.py` собирает его через эталонную модель в PyTorch BF16 и Optuna.

Будь памяти хватало, скорость всё равно была бы ниже: у 5070 Ti пропускная способность памяти 896 ГБ/с, вдвое
меньше, чем у 5090, так что ориентир — половина авторских цифр, и то на коротком контексте. 320K со всеми
весами в VRAM на 16 ГБ не помещается ни в каком движке.

Что можно перенести в наш патч `strata-inkling`:
1. **Эмбеддинги в закреплённой RAM.** У squid5090 таблица `embed` (BF16, 201 024 × 2304, 0.86 ГиБ) лежит в
   pinned-памяти, отображённой в адреса GPU (zero-copy), и на токен по PCIe читается одна строка в 4.6 КБ.
   В Strata она лежит в VRAM внутри `d_trunk`: `ink_gguf_loader.h` переводит `token_embd` в BF16, читает её
   `k_ink_embed_norm`. Освободившиеся 0.86 ГиБ можно отдать экспертам, 5.6 → ~6.4 ГиБ при том же 320K.
   По нашим замерам 6.2 ГиБ экспертов на 8K давали 2175 / 41.5 ток/с против 1941 / 38.2 при 5.6. Из трёх
   пунктов это самая дешёвая правка.
2. **Prompt-lookup драфтер.** Черновик берётся из уже прочитанного текста: кольцо последних 8 192 токенов и
   хеш-индекс, 320 КБ RAM, VRAM не нужна. DSpark у нас на 320K не окупился как раз из-за своего KV в VRAM,
   у prompt-lookup его нет. Выигрыш ожидаем на правках кода и цитировании результатов инструментов. Но
   проверка 8 токенов за раз задевает больше разных экспертов, а часть их у нас в RAM, так что прирост
   надо мерить. Проверка черновиков DSpark в Strata уже есть (`cuda/ink_spec.cuh`), нужен второй источник
   черновиков.
3. **LoopCD-Hidden**: после третьего прохода петли `h' = h3 + ω(h3 − h1)`, ω = 0.1–0.2. У авторов в режиме
   размышлений +2 задачи из 30 и на 5.5% меньше токенов размышлений, без размышлений результат хуже. Выборка
   маленькая, браться стоит после пп. 1–2 и проверять нашим бенчмарком агентских задач.

**Пункт 1 сделан (2026-11-25).** `STRATA_INK_HOST_EMBED=1` в патче движка: при загрузке GGUF таблица
`model.llm.embed.weight` вырезается из ствола (смещения тензоров после неё сдвигаются на её размер) и
копируется в `cudaHostAlloc(..., cudaHostAllocMapped)`. Оба места, где её читает `k_ink_embed_norm`
(основной проход и DSpark), берут адрес через `embed_ptr()`. Ствол в VRAM 3.29 → 2.37 ГБ. При разбиении
по нескольким GPU опция не действует.

Проверка: жадная генерация на 64 и 96 токенов (случайный промпт на 900 токенов и встроенный промпт движка)
совпала со старым движком токен в токен. При тех же 5.6 ГиБ экспертов скорость та же (8K: 1923 / 34.9 против
1932 / 35.0), то есть чтение строк эмбеддинга по PCIe ничего не стоит.

`--bench`, тот же день, RTX 5070 Ti, k8v4, prefill / генерация в ток/с:

| Движок, эксперты в VRAM | 8K | 320K (промпт 327 000) |
|---|---|---|
| старый, 5.6 ГиБ (1342 эксперта) | 1932 / 35.0 | 842 / 22.2 |
| новый, 6.0 ГиБ (1438) | **2053 / 38.2** | **877 / 24.8** |

На 6.4 ГиБ контекст 320K не режется, но генерация в конце контекста падает: VRAM занята на 15.2 из 15.9 ГиБ
(на 6.0 — 14.8). Поэтому в лаунчере 6.0 для 320K и 8.0 для 128K (раньше 8.0 резал контекст до 117K).

**Пункт 2 сделан (2026-11-25): prompt-lookup драфтер.** `STRATA_INK_LOOKUP=K` (1..15, в лаунчере 7) в
`ink_serve.h`, работает для одного потока без DSpark. Индекс в RAM: точный ключ из последних 3 токенов
(`STRATA_INK_LOOKUP_N`, 2..3) указывает на последнее место, где они уже встречались в промпте или ответе. Черновик —
до K токенов, которые шли следом. Индекс строится заново на каждый запрос (52K токенов истории — доли секунды).
Проверка та же, что у DSpark в общем пути: `snapshot_slot`, один `forward_batch` на черновик + 1 токен
(`forward_tree_verify` до 16 токенов), `verify_draft_logits` (при температуре > 0 точная выборка с отклонением),
`rollback_slot`. Длина черновика адаптивная: после промаха следующий черновик длиной «принято + 1», после полного
попадания длина удваивается до K. Без адаптивной длины эссе замедлялось на 6%.

Замер через API сервера, 320K-режим (эксперты 6.0 ГиБ), ток/с генерации. Задачи: переписать файл на 220 строк целиком

прогон; длина ответа между прогонами разная, разброс — несколько процентов.

|---|---|---|
| переписать файл (промпт 4.8K) | 44.6 / 44.5 | **67.9 / 65.4** |

Эссе ускоряется, потому что модель пишет черновик в размышлениях и потом переносит его в ответ. Единственный минус —

Тексты на температуре 0 с драфтером и без расходятся в первых строках, на развилках между почти равными токенами
(«rewrite the file» / «rewrite the whole file»): проверка нескольких токенов разом считает логиты чуть иначе, чем по

драфтера: два прогона одного движка с `LOOKUP=0` на температуре 0 тоже дали разные тексты. Контроль на финальной

## 4. Аблитерация своими руками: ресурсы

Heretic грузит модель в bf16: память ≈ 2 × params + активации.

| База | bf16 вес | Реально на 32 ГБ RAM + 16 ГБ VRAM? |
|---|---|---|
| Qwen3-8B | ~16 ГБ | Да, полностью на GPU почти впритык / auto-offload |
| Gemma-3-12B / Qwen3-14B | ~24–28 ГБ | Да, с выгрузкой слоёв в RAM (медленнее) |
| Mistral Small 24B | ~48 ГБ | Нет — брать готовый GGUF или машина с ≥64 ГБ RAM |

## 5. Оценка качества (обязательный шаг)

Аблитерацию нельзя делать «вслепую». `scripts/evaluate.py` меряет:

1. **Refusal rate** — доля отказов на наборе из ~40 провокационных промптов
   (детектор по фразам «I cannot», «Извините, я не могу» и т.п.).
2. **Сохранность интеллекта** — сравнение ответов на нейтральных бенчмарк-промптах
   (простые задачи по логике/математике/коду) до/после; при серверном режиме —
   сравнение по метрикам ответов, при локальном — KL-дивергенция (её считает
   сам Heretic при подборе параметров).

Критерий приёмки: refusal rate ≤ 5% на пробах, при этом базовые задачи решаются
на уровне исходной модели.
